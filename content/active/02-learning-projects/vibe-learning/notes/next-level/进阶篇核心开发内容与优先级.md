## 二、P0：立即做（高价值 + 低/中成本）

### 2.1 数据库持久化改造

**对应章节**：第 6 章「数据存在哪里」

**为什么是 P0：**
当前向量数据存在 `chroma-db/documents.json` 文件里，有几个问题：
- 数据量大了之后读写性能差
- 并发写入可能损坏
- 不方便备份和迁移
- 不支持复杂查询

**推荐方案：**
| 方案 | 难度 | 说明 |
|------|------|------|
| **SQLite + Prisma** | ⭐⭐ | 轻量、不用装服务、本地单文件，适合个人项目 |
| **PostgreSQL + pgvector** | ⭐⭐⭐ | 专业向量数据库扩展，功能强，但需要装服务 |
| **继续用 JSON** | ⭐ | 不改也行，先凑合用，数据量大了再迁 |

**执行步骤：**

```
1. 安装 Prisma 和数据库驱动
   └─ pnpm add prisma @prisma/client
   └─ pnpm prisma init

2. 设计数据模型（schema.prisma）
   ├─ Document：文档元数据（标题、来源、上传时间）
   ├─ DocumentChunk：文档片段（内容、向量、所属文档）
   └─ ChatLog：对话日志（问题、回答、Token 消耗）

3. 数据迁移
   └─ 把现有的 documents.json 导入到新数据库

4. 改造 chroma.ts
   └─ 把内存存储换成数据库存储
   └─ 保持接口不变，上层代码不用改
```

**验收标准：**
- 启动服务后数据不丢失
- 上传文档正常入库
- 查询速度不低于当前水平
- 可以用 Prisma Studio 查看数据

---

### 2.2 API 规范化 & 错误处理

**对应章节**：第 7 章「连接前后端」

**为什么是 P0：**
当前 API 是能跑就跑的状态，没有统一的错误处理，前端也不好判断是哪里错了。

**要做的事：**

```
1. 统一返回格式
   ├─ 成功：{ code: 0, data: ..., message: "ok" }
   └─ 失败：{ code: 错误码, data: null, message: "错误描述" }

2. 错误码规划
   ├─ 0：成功
   ├─ 4000-4999：客户端错误（参数不对、权限不够）
   └─ 5000-5999：服务端错误（数据库挂了、AI 调用失败）

3. 请求校验
   └─ 用 zod 或 joi 校验请求参数
   └─ 参数不对直接返回 4001，不往下走

4. 全局错误处理中间件
   └─ 所有异常统一捕获，返回标准格式
   └─ 记录错误日志，方便排查
```

**验收标准：**
- 所有接口返回格式统一
- 参数错误时返回明确的错误信息
- 服务端报错不会返回堆栈信息给前端
- 错误有日志记录

## 三、P1：尽快做（高价值 + 中成本）

### 3.1 鉴权 & API Key 管理

**对应章节**：第 8 章「谁能访问我的数据」

**为什么是 P1：**
现在接口谁都能调，API Key 也直接写在 .env 里。如果部署到公网，很容易被滥用。

**要做的事：**

```
1. API Key 鉴权
   ├─ 生成几个 API Key（给不同的人用）
   ├─ 请求头里带 x-api-key
   └─ 中间件校验，不对就返回 401

2. 环境变量安全
   ├─ 所有密钥都从环境变量读
   ├─ .env 文件加入 .gitignore（已经做了）
   └─ 部署时通过平台的环境变量配置

3. （可选）用户系统
   ├─ 注册 / 登录
   ├─ 每个人有自己的知识库
   └─ 个人项目暂时不用搞这么复杂
```

**验收标准：**
- 不带 API Key 请求会被拒绝
- 错误的 API Key 会被拒绝
- API Key 不会出现在代码或日志里

---

### 3.2 CI/CD 自动部署

**对应章节**：第 12 章「无服务器自动部署」

**为什么是 P1：**
现在部署要手动操作，麻烦还容易忘。配置好 CI/CD 之后，提交代码自动部署。

**推荐方案：**
| 方案 | 难度 | 说明 |
|------|------|------|
| **GitHub Actions + 云服务器** | ⭐⭐ | 灵活，但需要自己配 |
| **Vercel / Netlify** | ⭐ | 前端一键部署，后端用 Serverless Functions |
| **CNB 自动构建** | ⭐ | 腾讯云 CNB 自带，和代码仓库联动 |

**执行步骤：**

```
1. 选一个部署平台（推荐先用 Vercel 试试前端）
2. 关联 GitHub 仓库
3. 配置构建命令和输出目录
4. 配置环境变量
5. 提交代码，看是不是自动构建部署
6. 后端服务另说，先把前端自动化了
```

**验收标准：**
- 推送到 main 分支自动构建
- 构建失败有通知
- 部署成功后可以直接访问
- 环境变量安全配置，不写在代码里

## 四、P2：有空做（中价值 + 中/低成本）

### 4.1 测试体系

**对应章节**：第 9 章「功能测试」

**为什么是 P2：**
有测试改代码更放心，但个人项目优先级可以放低一点。先保证核心功能有测试就行。

**建议覆盖的测试点：**

```
1. 单元测试
   ├─ 文本分片逻辑对不对
   ├─ 相似度计算对不对
   └─ 错误处理中间件

2. 接口测试
   ├─ 文档上传接口
   ├─ 问答接口
   └─ 鉴权逻辑

3. 不需要做的
   ├─ UI 自动化测试（成本太高）
   ├─ 端到端测试（个人项目没必要）
   └─ 100% 覆盖率（追求 80% 关键路径覆盖就行）
```

**工具推荐：**
- 测试框架：Vitest 或 Jest
- 接口测试：supertest
- 覆盖率：c8

---

### 4.2 Git 规范 & 分支策略

**对应章节**：第 11 章「协作开发」

**为什么是 P2：**
现在是个人项目，乱一点也没事。但项目变大、或者有人加入之后，规范就很重要了。

**建议的规范：**

```
1. 分支策略
   ├─ main：生产环境代码，永远可部署
   ├─ dev：开发环境代码
   └─ feature/xxx：功能分支，从 dev 切出来
   （个人项目可以简化成 main + feature 两级）

2. Commit message 规范
   ├─ feat: 新功能
   ├─ fix: 修 bug
   ├─ docs: 文档
   ├─ refactor: 重构
   ├─ perf: 性能优化
   └─ chore: 构建/工具相关

3. 其他
   ├─ .gitignore 配好，别把 node_modules、.env 提交了
   ├─ 大文件不要往 Git 里塞
   └─ 敏感信息（API Key、密码）绝对不能提交
```

**为什么是 P3：**

**对应章节**：第 10 章「公网访问」、第 13 章「域名解析」、第 14 章「部署到服务器」

**为什么是 P3：**

以下内容进阶篇有讲，但**对当前 RAG 知识库项目意义不大**，暂时不用管：

### 6.1 被剔除的内容 & 原因

| 内容 | 对应章节 | 剔除原因 |
|------|----------|----------|
| **环境搭建（Node.js、Git 安装）** | 第 1 章 | 已经搭好了，不需要再看 |
| **AI 工具基础用法** | 第 2 章 | 已经在用 AI 开发了，属于入门内容 |
| **PRD 文档写法** | 第 3 章 | 项目已经有了，PRD 是新项目才需要的 |
| **UI/UX 设计基础** | 第 5 章 | 内部工具，能用就行，不需要花太多时间在设计上 |
| **SEO 优化** | 第 15 章 | 知识库工具不需要搜索引擎流量 |
| **数据统计 / 埋点** | 第 15 章 | 个人项目，没有分析用户行为的需求 |
| **用户反馈收集** | 第 16 章 | 还没有用户，收集什么反馈 |
| **团队协作 / Code Review** | 第 11 章 | 个人项目，没有团队 |
| **域名备案 / DNS 解析细节** | 第 13 章 | 不上线公网就不需要 |
| **VPS 运维 / 1Panel** | 第 14 章 | 用 Serverless 部署更简单，不用管服务器运维 |
| **移动端适配细节** | 第 5 章（部分） | 主要在电脑上用，移动端能看就行 |

### 6.2 什么时候可以捡回来

- **想做新的 Side Project**：可以从 PRD 开始，完整走一遍进阶篇的流程
- **项目有真实用户了**：用户反馈、数据统计、SEO 就有意义了
- **团队有人加入了**：协作规范、Code Review 就需要了
- **要商业化了**：域名、备案、服务器运维、安全都得搞
