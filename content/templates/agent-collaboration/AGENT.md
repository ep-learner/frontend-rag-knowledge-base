# AGENT.md — 人 + Agent 协作架构改造指南

> 如果你是 AI Agent，接手这个项目前，请先读完本文。
> 预计阅读时间：5 分钟。
>
> **你的任务**：把现有项目改造成「人 + Agent 协作」的架构模式。
> **核心目标**：让 Agent 知道什么该改、什么不该改、加内容去哪加、怎么跟人配合。

---

## 一、这是什么模式（4 个核心特征）

### 1. 可变与不可变完全隔离
- **架构层**（代码/基础设施）：稳定，低频改动，人来主导
- **内容层**（业务内容/函数/应用）：活跃，高频迭代，Agent 主力区
- Agent 不要随便动架构层的东西

### 2. 协议驱动
- 内容层的内容只要符合统一协议（manifest/格式约定），就能被系统识别和渲染
- **加内容 = 加文件，不用改代码**
- 所有内容在一个入口可触达，没有孤岛

### 3. 升降级机制
- 内容有生命周期：`_pending/`（待整理） → 草稿 → 正式 → `archive/`（归档）
- 拿不准的先放草稿区，别硬塞到正式区
- 不用了先归档，别直接删

### 4. 人 + Agent 分工
- **人**：决策、验收、处理复杂问题、定方向
- **Agent**：执行、整理、生成脚手架、维护一致性、干重复劳动

## 二、目标目录结构

```
your-project/
├── 🔧 架构层（低频，人主导）
│   ├── packages/                 核心代码（server + client，或你项目的实际结构）
│   ├── dev.ps1 / dev.sh          一键启动脚本
│   ├── README.md                 给人看的项目介绍
│   ├── ARCHITECTURE.md           技术架构详解
│   └── AGENT.md                  ⭐ 你正在看的
│
├── 📦 工作区（高频，Agent 主力区）
│   ├── AGENT.md                  ⭐ 工作区指南（加内容前必读）
│   ├── DELIVERY_PROTOCOL.md      内容协议（怎么组织内容才能被识别）
│   ├── archive/                  归档区（不用的挪这）
│   └── active/                   活跃内容
│       ├── 01-xxx/                原子单元（函数/组件/知识点... 你自己定）
│       ├── 02-xxx/                组合单元（应用/页面/专题... 你自己定）
│       └── 03-drafts/             草稿/待整理
│           └── _pending/          ⚡ Agent 整理入口（下划线开头，不被索引）
│
├── 💡 计划层（想法和待办）
│   ├── active/                    进行中的计划、backlog
│   └── archive/                   已完成/放弃的计划
│
├── 🧠 记忆层（Agent 工作记忆）
│   ├── current-state.md           ⭐ 当前状态、进度、待办（必更）
│   ├── work-log/                  每日日志（日更）
│   └── playbook/                  操作手册（命令速查、踩坑记录）
│
└── 🤖 技能层
    └── .trae/skills/
        ├── project-init/           新对话初始化
        ├── commit-with-check/      提交前检查
        └── ...                     业务相关 skill
```

### 每层一句话

| 层 | 干什么 | Agent 活跃度 |
|----|--------|-----------|
| 架构层 | 核心代码、基础设施 | 低（人主导） |
| 工作区 | 业务内容、原子单元、组合单元 | 高（Agent 主力） |
| 计划层 | 想法、待办、临时任务 | 中 |
| 记忆层 | Agent 的工作记忆、进度追踪 | 高（每次必更） |
| 技能层 | Agent 的能力扩展 | 中（按需加） |

## 三、核心设计原则（重要！）

### 1. 协议驱动：加内容不改代码
- 内容是纯文件（Markdown + JSON + 代码文件）
- 有一套统一的协议（比如 manifest.json 约定格式）
- 新增内容 = 新增文件，不用改前后端代码
- 协议是整个架构的核心，定好了就别轻易改

### 2. 三层升降级
```
_pending/  →  草稿区  →  正式区  →  archive/
  素材         半成品       成品         归档
```
- 拿不准的先放 `_pending/`，整理后升上去
- 不用了的移到 `archive/`，别直接删
- 正式区的内容必须符合协议规范

### 3. 记忆层：换 Agent 也能接上
**必更文件：**
- `current-state.md` — 当前进度、待办、已知问题（每次有状态变化都更）
- `work-log/YYYY-MM-DD.md` — 每天做了什么、关键决策

### 4. 无孤岛原则
所有内容都在一个入口页面能找到，不能有内容藏在角落里没人知道。

## 四、你的任务：改造现有项目

### 第 1 步：分析现状（先别动手！）
搞清楚：
- 现有项目的技术栈？
- 哪些是「原子单元」？（函数/组件/知识点...）
- 哪些是「组合单元」？（应用/页面/专题...）
- 现在内容存在哪？数据库？散在代码里？文件里？
- 有没有现成的前端入口/管理后台？

**产出**：在 `agent-memory/current-state.md` 里记录现状分析。

### 第 2 步：定方案
基于现状，给出：
- 工作区分几层？每层叫什么？
- 协议怎么定？（原子单元格式、组合单元 manifest）
- 现有内容怎么迁？
- 改造分几步？每步做什么？

**产出**：一份改造方案文档，找人确认后再动手。

### 第 3 步：搭骨架
先把目录结构建起来，空的也行：
- workspace/（active + archive + templates）
- agent-memory/（current-state + work-log）
- plans/（active + archive）
- .trae/skills/（project-init + commit-with-check 先配上）
- 根 AGENT.md（就是这个文件，根据项目实际调整）

### 第 4 步：定义协议（最重要！）
写 `workspace/DELIVERY_PROTOCOL.md`，说清楚：
- 原子单元的目录结构是怎样的？需要哪些文件？
- 组合单元的 manifest.json 有哪些字段？
- 命名规范是什么？
- 前端/系统怎么识别和渲染？

**协议定好了，后面加内容就不用改代码了。**

### 第 5 步：做最小可行版（MVP）
先做一个最小版本跑通流程：
1. 后端能读 workspace/，列出分类/列表/详情
2. 前端能渲染出来（或 API 能调用）
3. 能加一个测试内容验证流程通

### 第 6 步：迁移内容
把现有内容按协议整理，迁到 workspace/ 对应目录。

## 五、提交代码前检查清单

**在 `git commit` 之前，过一遍：**

### 1. 如果你改了代码（架构层）
- [ ] 有没有对应的功能文档需要更新？（README / ARCHITECTURE）
- [ ] 如果改了 API，API 文档更新了吗？
- [ ] 如果改了协议，DELIVERY_PROTOCOL.md 更新了吗？

### 2. 如果你加了/改了内容（工作区）
- [ ] 内容放对目录了吗？（原子层/组合层/草稿）
- [ ] 命名符合规范吗？
- [ ] 如果是组合单元，manifest 补了吗？

### 3. 如果你改了架构/目录结构
- [ ] 根 AGENT.md 的映射表更新了吗？
- [ ] README 项目结构更新了吗？
- [ ] workspace/AGENT.md 对应更新了吗？

### 4. 通用检查
- [ ] agent-memory/current-state.md 同步了吗？
- [ ] 今天的 work-log 写了吗？
- [ ] 有没有敏感信息（API Key、密码）提交了？
- [ ] 测试能过吗？（如果有测试）

按顺序读：
1. 现有项目的 README — 了解业务
2. 现有项目代码结构 — 了解技术栈
3. 本文 AGENT.md — 就是这个（改造目标）
4. agent-memory/current-state.md — 当前进度（如果已有）

然后从第 1 步：分析现状，开始。
